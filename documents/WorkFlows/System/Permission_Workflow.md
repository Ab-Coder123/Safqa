# Permission Workflow

## Purpose
The Permission Workflow manages access control, resource ownership checks, and administrative privileges in Safqa. It prevents unauthorized users from modifying data and enforces security boundaries.

## Business Overview
Securing resources is essential for marketplace trust:
1. Standard users can only modify resources they own (their listings, profile, settings).
2. Super Admins possess full system rights to manage any listing, category, or account.
3. Access is verified on every request to prevent unauthorized actions.

## Actors
- **USER**: Can manage their own listings, profile, and settings.
- **SUPER ADMIN**: Accesses all administrative APIs and dashboards.
- **System**: Parses role claims, compares resource IDs, and grants or denies access.

## Preconditions
- The requesting user is authenticated and has a valid JWT token.
- The target resource exists in the database.

## Trigger
- A user sends a request to modify a resource (e.g. edit listing, delete favorite).
- A user attempts to call an admin API.

## Main Workflow (Happy Path)
1. **Send Request**: User A requests to edit a product listing.
2. **Retrieve Token Claims**: The System extracts User A's ID and role from the JWT header.
3. **Inspect Owner**: The System retrieves the product listing from the database and checks the owner ID.
4. **Compare IDs**: The System verifies that the product's `user_id` matches User A's ID.
5. **Grant Access**: The System authorizes the update request.
6. **Apply Changes**: The modification is processed, and success is returned.

## Alternative Flows
### Administrative Access Override
1. Super Admin requests to archive User B's product listing.
2. The System checks the admin's JWT claims and identifies `role === 'SUPER_ADMIN'`.
3. The System bypasses ownership checks and authorizes the request.
4. The product is archived, and the action is logged in the audit trail.

## Exception Flows
### Ownership Mismatch
- **Trigger**: User A attempts to edit User B's listing by sending a request using User B's product ID.
- **System Behavior**: The System detects that the product owner ID does not match User A's ID, blocks the action, returns a `403 Forbidden` error, and logs a security exception.

## Business Rules
- **USER Restrictions**: Standard users can only modify resources (listings, favorites, conversations) they created.
- **SUPER ADMIN Authority**: Super Admins can manage any resource to moderate the platform.
- **Role Limits**: The system supports only two roles: `USER` and `SUPER_ADMIN`. There are no intermediate roles.

## State Changes
This workflow enforces access rules and does not modify entity states directly.

## Database Impact
- **User Entity**: Reads roles and status values.
- **Product Entity**: Reads owner IDs to verify access.

## Notifications
No user notifications are generated by this workflow.

## Permissions
- **Authenticated USER**: Access to their own data.
- **SUPER ADMIN**: Full access to all platform resources.

## Security Considerations
- **Secure Token Checks**: Read user IDs from verified JWT tokens instead of request parameters to prevent ID spoofing.
- **Prisma Ownership Filters**: Include user ID filters in SQL queries (e.g. `WHERE id = productId AND user_id = userId`) to ensure users can only update their own listings.

## Audit & Logging
- **Access Violations**: Log all unauthorized access attempts (User ID, Endpoint, Resource ID, timestamp) to identify potential attacks.

## Future Improvements
- **Role-Based Access Control (RBAC)**: Support additional moderation roles (e.g., Moderator, Support Agent) in future updates.

## Related Workflows
- **Authentication Workflow**: Provides user credentials and role claims.
- **Product Management Workflow**: Calls ownership checks during edits/deletions.

## Summary
The Permission Workflow secures all data in Safqa. By enforcing strict ownership checks, parsing JWT claims, and routing administrative overrides, it protects user resources and keeps platform controls secure.
